# Анализ и коррекция P1.2 — Docker-инфраструктура

## Короткий вердикт

**Идея правильная** (Docker снимает барьер входа для опенсорса — это стандарт индустрии), но **план написан «до» реального кода** и содержит **несколько противоречий с фактами проекта** и **одну архитектурную ошибку**. Если реализовывать «как есть» — получим **нерабочий или опасно работающий** контейнер.

Главные проблемы:
- **Монолит (Вариант A)** — плохое решение для этого проекта: whisper уже запускается как **отдельный HTTP-сервер** (два инстанса, порты 8081/8082), а chat-модель — **внешний** llama-server/Ollama. Монолит «backend + whisper + LLM» **невозможен** без изменения архитектуры.
- **`host.docker.internal`** — на Linux **не работает** из коробки (нужен `extra_hosts`), а на Windows/macOS — работает. План упоминает это в «Ограничениях», но **не** в `docker-compose.yml`.
- **`deploy.resources.reservations.devices`** — **не работает** в `docker compose up` (это для Swarm). Нужен `runtime: nvidia` + `NVIDIA_VISIBLE_DEVICES=all` или Compose v2.30+ с `deploy` в non-swarm (не везде).
- **Whisper 2 инстанса в одном контейнере** — entrypoint-скрипт с `&` — плохо: логи смешиваются, один упал — второй живёт, healthcheck сложный. **Два контейнера** — правильно.
- **SQLite в volume на macOS/Windows** — **сильно медленнее** (известная проблема Docker Desktop, план это упоминает, но не решает — предлагаю решение).
- **PAT / `.env`** — план копирует `server/.env` в контейнер (`env_file`), а там **секреты** (в будущем — `GIT_PAT_ENCRYPTION_KEY` из P1.1). `.env` в образе — плохо.
- **GPU-проброс** — работает только NVIDIA Linux; macOS (Apple Silicon) — **никакого GPU**, только CPU; Windows WSL2 — работает, но требует NVIDIA driver **на хосте** + WSL2 + Docker Desktop.

Ниже — разбор по пунктам + **готовый переработанный план**.

## Проблемы (по убыванию важности)

### 🔴 P1. Монолит vs Микросервисы — **монолит неверен для этого проекта**

**План:** «Рекомендация: Вариант A (монолит)».

**Реальность проекта:**
- **whisper** — уже **внешний HTTP-сервер** (`WHISPER_USER_URL`, `WHISPER_INTERLOCUTOR_URL` в `aiHelperController.js`). Два инстанса, порты 8081/8082. Это **не** часть Node.js-процесса — это отдельные процессы.
- **chat-модель** — **внешний** llama-server (порт 8080) или Ollama (11434). Не в Node.js.
- **Node.js-процесс** (`server.js`) — только backend + frontend static. Он **уже** микросервис по архитектуре (общается с whisper и LLM по HTTP).

**Монолит** в плане означает: «один контейнер, в нём Node.js + whisper (2 инстанса) + LLM». Но:
- LLM **нельзя** упаковать в тот же контейнер (это отдельный llama.cpp / Ollama, у него своё GPU-управление, свои volumes с моделями ~10 ГБ).
- Whisper **можно** упаковать (два инстанса в одном контейнере через entrypoint с `&`), но это **плохо**: логи смешиваются, healthcheck сложный, один упал — второй живёт, ресурсы делятся.
- Node.js + whisper в одном контейнере — **смешение ответственности** (Node.js обновляется чаще, whisper — реже; разные base images: Node.js `node:20-slim`, whisper — `nvidia/cuda:...`).

**Правильно — микросервисы (Вариант B)**, но **не в том виде, как в плане**:

```
docker-compose.yml
├── app          — Node.js backend + frontend static (один контейнер, порт 3000)
├── whisper-user — whisper.cpp server (порт 8081)
├── whisper-interlocutor — whisper.cpp server (порт 8082)
├── ollama       — опционально, profile
└── (llama.cpp на хосте — через host.docker.internal или extra_hosts)
```

**Почему whisper — два контейнера, а не один с двумя инстансами:**
- Разные модели? Нет, одна (`ggml-medium.bin`), но **разные входы** (user mic vs system audio). Один сервер может обрабатывать оба — **не нужно два**. **Упрощение:** **один** whisper-контейнер, `WHISPER_USER_URL=http://whisper:8081/inference`, `WHISPER_INTERLOCUTOR_URL=http://whisper:8081/inference` — **один** URL. Сейчас в `aiHelperController.js` **два** URL — но это **исторически** (два инстанса для параллельности). Для Docker MVP — **один** whisper-контейнер, **один** URL, оба `WHISPER_*_URL` указывают на него. Если понадобится параллельность — второй контейнер позже.
- Один контейнер = один процесс = простой healthcheck, чистые логи, один GPU-проброс.

**Итог P1:** **микросервисы**: `app` (Node.js) + `whisper` (один, опционально два) + `ollama` (profile). **Не** монолит.

### 🔴 P2. GPU-проброс — `deploy.resources.reservations.devices` **не работает** в `docker compose up`

**План:**
```yaml
deploy:
  resources:
    reservations:
      devices:
        - driver: nvidia
          count: 1
          capabilities: [gpu]
```

**Реальность:** `deploy` — **Swarm-only** секция в Compose. В `docker compose up` (non-swarm) она **игнорируется** (Compose v2.30+ частично поддерживает, но не везде). Правильно:

```yaml
services:
  whisper:
    runtime: nvidia
    environment:
      - NVIDIA_VISIBLE_DEVICES=all
      # или - NVIDIA_VISIBLE_DEVICES=0 для конкретной GPU
```

Или Compose v2.30+ с `gpus: all` (новый синтаксис):
```yaml
services:
  whisper:
    gpus: all
```

**Без этого** GPU **не пробросится**, whisper будет на CPU (медленно, но работает).

**Также:** для NVIDIA нужен `nvidia-container-toolkit` на хосте + `nvidia-ctk runtime configure --runtime=docker` + рестарт Docker. README должен это явно указать (план упоминает, но в troubleshooting, а не в Prerequisites).

### 🔴 P3. `host.docker.internal` — на Linux **не работает** без `extra_hosts`

**План:** `LLAMA_CPP_URL=http://host.docker.internal:8080` — с комментарием «Если llama.cpp на хосте». В «Ограничениях»: «Linux: нужно добавить `--add-host=host.docker.internal:host-gateway`».

**Проблема:** в `docker-compose.yml` **этого нет**. На Linux контейнер **не увидит** `host.docker.internal` → `ECONNREFUSED` → provider fallback → 503.

**Правильно:**
```yaml
services:
  app:
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

Это **работает** на Linux (Docker 20.10+), **не мешает** macOS/Windows (там и так есть). **Обязательно** в `docker-compose.yml`, не только в README.

### 🟠 P4. `env_file: ./server/.env` — секреты в образе

**План:** `env_file: - ./server/.env`. Это **не** копирует `.env` в образ (он монтируется при запуске), но:
- `.env` содержит **все** переменные, включая будущий `GIT_PAT_ENCRYPTION_KEY` (P1.1) и `WHISPER_*`.
- Если пользователь запускает `docker compose up` — `.env` читается с хоста, ок.
- Но `Dockerfile` **не должен** `COPY .env` (иначе секреты в образе — утечка при `docker push`).

**Правильно:**
- `.env` — **не** в образе (`.dockerignore` содержит `.env`, `.env.*`, `server/.env`).
- `env_file: ./server/.env` — **только** для `docker compose up` (runtime).
- В `.env.example` — **без** секретов (пустые `GIT_PAT_ENCRYPTION_KEY=`).

**Также:** `OLLAMA_URL=http://ollama:11434` в `environment` **перезаписывает** `env_file`? Нет, `env_file` + `environment` — `environment` **выигрывает**. Это ок для `ollama` (внутренний DNS), но **путает** (в `.env` `OLLAMA_URL=http://localhost:11434`, в compose — `http://ollama:11434`). **Убрать** `environment`-дубли, оставить только `env_file` + **явные** переопределения с комментарием.

### 🟠 P5. SQLite в volume на macOS/Windows — **медленно**

**План** упоминает в «Рисках»: «SQLite в volume может быть медленнее, чем нативно (macOS/Windows)». Но **не решает**.

**Реальность:** Docker Desktop на macOS/Windows использует **virtiofs/gRPC FUSE** для bind-mount — SQLite (WAL, fsync) **сильно** тормозит (в 5–10 раз на запись). На Linux — нативно, ок.

**Решения:**
- **Named volume** для `data/` (не bind-mount). Named volumes на macOS/Windows — **быстрее** bind-mount (Docker управляет хранилищем). Минус: пользователь не видит `chat.db` напрямую (нужен `docker cp` / `docker volume inspect`).
- **Bind-mount** для `data/` — удобно для backup (файл виден), но медленно на macOS/Windows.
- **Гибрид:** `./data` bind-mount (для пользователя), но **документировать** «на macOS/Windows — медленно, для production используйте Linux».

**Рекомендую:** **bind-mount `./data`** (простота, backup, пользователь видит файлы) + **предупреждение** в README. Named volume — опционально (`--profile fast-data`? overkill). **Зафиксировать.**

### 🟠 P6. `Dockerfile` — whisper.cpp компиляция

**План:** «Stage 2: Build whisper.cpp. Base: `nvidia/cuda:12.2.0-devel-ubuntu22.04`».

**Проблемы:**
- **CUDA 12.2** — устарел (сейчас 12.4+). Но для whisper.cpp — **любая** CUDA 11.8+ работает. Фиксировать `12.2.0` — ок, но **проверить**, что whisper.cpp v1.5.0 собирается с 12.2.
- **`WHISPER_CUDA=1`** — правильно, но нужен `-DGGML_CUDA=1` (новый флаг, whisper.cpp v1.5+ перешёл на ggml).
- **Размер образа:** CUDA-devel ~7 ГБ. Multi-stage **обязателен** (runtime — `nvidia/cuda:12.2.0-runtime` ~2 ГБ).
- **Модель `ggml-medium.bin`** (~1.5 ГБ) — **не** в образе (иначе образ ~10 ГБ). Volume `./models/` + **скачивание при первом запуске** (entrypoint: если файла нет — `wget`). Или — README «скачай модель».

**Правильно:**
- Stage 1: frontend build (`node:20-alpine`).
- Stage 2: whisper build (`nvidia/cuda:12.2.0-devel-ubuntu22.04`, `-DGGML_CUDA=1`).
- Stage 3: whisper runtime (`nvidia/cuda:12.2.0-runtime-ubuntu22.04`, копирует `whisper-server`).
- Stage 4: app runtime (`node:20-slim`, копирует `server/` + `frontend/dist/`).
- **Отдельные** Dockerfile: `Dockerfile.app` (Node.js) и `Dockerfile.whisper` (CUDA) — **не** один multi-stage на всё (разные base images, разная частота обновления).

**План** пишет «один Dockerfile, 3 stage» — **неудобно** (whisper пересобирается при изменении frontend). **Два Dockerfile** — правильно.

### 🟡 P7. Entrypoint «backend + whisper (2 инстанса)»

**План:** «Entrypoint: скрипт, который запускает backend + whisper (2 инстанса)».

**Проблема:** если это **один** контейнер (монолит), entrypoint с `&`:
- Логи смешиваются (backend + whisper), сложно дебажить.
- Один процесс упал — второй живёт (нужен supervisor, `s6-overlay`, `supervisord`).
- Healthcheck сложный (два порта).
- GPU-проброс — для whisper, но backend GPU не нужен — **лишнее**.

**Правильно (микросервисы):** **отдельные контейнеры**, каждый со своим entrypoint:
- `app` — `node src/server.js`.
- `whisper` — `whisper-server --model /models/ggml-medium.bin --port 8081`.

Никаких `supervisord`, `s6-overlay` — Docker Compose сам управляет жизненным циклом.

### 🟡 P8. `DEFAULT_PROVIDER=${DEFAULT_PROVIDER:-ollama}` — конфликт с `.env`

**План:** в `environment` — `DEFAULT_PROVIDER=${DEFAULT_PROVIDER:-ollama}`. Это **bash-подстановка** (Compose), берёт из **хостового** окружения (не из `env_file`). Если пользователь задал `DEFAULT_PROVIDER=llama_cpp` в `server/.env` — **не подхватится** (Compose не читает `env_file` для подстановки в `environment`).

**Правильно:** **убрать** `${DEFAULT_PROVIDER:-ollama}` из `environment`, оставить только `env_file: ./server/.env`. Если нужно переопределение — `docker compose run -e DEFAULT_PROVIDER=...` (явно). **Зафиксировать.**

### 🟡 P9. `OLLAMA_URL=http://ollama:11434` vs `localhost`

**План:** в `environment` — `OLLAMA_URL=http://ollama:11434` (внутренний DNS). Но в `.env.example` — `OLLAMA_URL=http://localhost:11434` (как сейчас в `providers.js`). **Конфликт**.

**Правильно:**
- В `.env.example` — `OLLAMA_URL=http://localhost:11434` (для native-запуска).
- В `docker-compose.yml` (профиль `ollama`) — `environment: OLLAMA_URL=http://ollama:11434` (переопределение для контейнера).
- В README — объяснить: «native — localhost, Docker — ollama:11434, Compose сам подставит».

**Зафиксировать.**

### 🟡 P10. `CONTEXT_BASE_DIR` — Windows path

**План:** `${CONTEXT_BASE_DIR}:/projects` — bind-mount. На Windows путь `C:\Users\...\progs` — **не** работает в `docker-compose.yml` (нужен `C:/Users/.../progs` или `/c/Users/.../progs` в WSL2). На macOS — `/Users/.../progs` — ок. На Linux — `/home/.../progs` — ок.

**Правильно:** в README — **явно** указать формат для Windows (`C:/Users/.../progs` или WSL2 `/mnt/c/Users/.../progs`). В `.env.example` — комментарий.

### 🟡 P11. Healthcheck — **не описан**

**План** не упоминает `healthcheck`. Без него:
- `docker compose up -d` возвращает управление **до** готовности app.
- Пользователь открывает `localhost:3000` — 502/connection refused.

**Правильно:** `healthcheck` для `app` (`wget -qO- http://localhost:3000/api/providers || exit 1`), для `whisper` (`curl -f http://localhost:8081/health`), для `ollama` (`ollama list`). `depends_on: condition: service_healthy` — где нужно (app → whisper, app → ollama если profile).

### 🟡 P12. `depends_on: - ollama` — **сломается** без профиля

**План:** `depends_on: - ollama` — но `ollama` в **профиле** `ollama`. Если запустить `docker compose up` **без** `--profile ollama` — Compose **ошибка** «service ollama not found» (или предупреждение, зависит от версии). `app` **зависит** от `ollama`, но `ollama` **не запущен** → `app` не стартует.

**Правильно:** **убрать** `depends_on: ollama` из `app` (app **не должен** зависеть от опционального сервиса). `providerMiddleware` уже делает fallback (503 → другой провайдер). Если Ollama не запущена — `OLLAMA_ENABLED=false` в `.env` или fallback на `llama_cpp`. **Зафиксировать.**

### 🟢 P13. Мелочи

- **`whisper.cpp@v1.5.0`** — проверить актуальную версию (v1.6+ уже есть). Фиксировать **конкретный** тег (не `master`).
- **`node:20.11-slim`** — ок, но для `better-sqlite3` (native module) нужен `python3`, `make`, `g++` в build-stage (иначе `node-gyp` упадёт). В runtime — **не** нужны (binary уже собран).
- **`pnpm`** — в Dockerfile: `corepack enable` (Node 20+ включает corepack) + `corepack prepare pnpm@10 --activate`.
- **`.dockerignore`** — **обязателен**: `node_modules`, `dist`, `.git`, `data`, `models`, `*.log`, `.env`, `server/.env`, `temp_audio`, `uploads`.
- **`Dockerfile` — non-root user** — правильно (`USER node` или `USER app`), но `better-sqlite3` + volume permissions — надо `chown` в Dockerfile.
- **`./models/ggml-medium.bin`** — если файла нет, `whisper-server` упадёт. Entrypoint: `if [ ! -f /models/ggml-medium.bin ]; then echo "Download model"; exit 1; fi` — **явная ошибка** с инструкцией, не молчаливый краш.
- **`--add-host=host.docker.internal:host-gateway`** — в `docker-compose.yml` (`extra_hosts`), **не** в README только.
- **`restart: unless-stopped`** — для всех сервисов (сейчас не везде).
- **`logging`** — `driver: json-file`, `max-size: 10m`, `max-file: 3` (иначе логи растут).
- **Windows WSL2** — `CONTEXT_BASE_DIR` через `/mnt/c/...` — **медленно** (9p filesystem). Рекомендую **WSL2-путь** (`/home/user/...`) для проектов, если возможно. Упомянуть.
- **`ollama pull`** — в README `docker compose exec ollama ollama pull qwen2.5-coder:7b` — правильно, но **модель ~4.7 ГБ**, первый pull **долгий**. Упомянуть.

## Переработанный план (готов к сохранению)

# Plan: Docker Infrastructure (P1.2) — Final

## Overview

Снять барьер входа для опенсорса: одна команда `docker compose up -d` поднимает `app` (Node.js backend + frontend static), `whisper` (HTTP-сервер распознавания) и **опционально** `ollama`. LLM-провайдер `llama.cpp` — **на хосте** (через `host.docker.internal`) или `ollama` в контейнере (profile). Архитектура — **микросервисы**, не монолит: проект **уже** общается с whisper и LLM по HTTP, упаковывать их в один контейнер — смешение ответственности и лишние проблемы.

**Ключевые решения:**
- **Микросервисы:** `app` + `whisper` (+ `ollama` profile). Не монолит.
- **Один whisper-контейнер** (не два): оба `WHISPER_*_URL` указывают на него (`http://whisper:8081/inference`). Второй инстанс — позже, если понадобится параллельность.
- **GPU:** `runtime: nvidia` + `NVIDIA_VISIBLE_DEVICES=all` (не `deploy.resources` — не работает в `compose up`).
- **`extra_hosts: host.docker.internal:host-gateway`** — для Linux (llama.cpp на хосте).
- **`env_file: ./server/.env`** — секреты **не** в образе (`.dockerignore`).
- **`depends_on`** — только `app → whisper` (healthcheck). **Без** `ollama` (опциональный).
- **`healthcheck`** — для всех сервисов.
- **CPU-only** — отдельный `Dockerfile.whisper` с `ARG USE_CUDA=false`.

## Container Architecture

```
docker-compose.yml
├── app          — Node.js 20 + Express + frontend static
│   ├── Port: 3000
│   ├── Volumes: ./data (SQLite + uploads)
│   ├── extra_hosts: host.docker.internal:host-gateway
│   └── Depends: whisper (healthy)
├── whisper      — whisper.cpp server (HTTP)
│   ├── Port: 8081
│   ├── Volumes: ./models (ggml-*.bin)
│   ├── runtime: nvidia (для GPU)
│   └── Healthcheck: curl /health
└── ollama       — опционально (profile: ollama)
    ├── Port: 11434
    ├── Volume: ollama-models
    └── runtime: nvidia
```

**LLM на хосте** (llama.cpp, порт 8080) — `app` обращается через `http://host.docker.internal:8080`. **LLM в контейнере** (ollama) — `app` обращается через `http://ollama:11434`.

## Dockerfiles (два, не один)

### `Dockerfile.app` — Node.js + frontend

```dockerfile
# Stage 1: build frontend
FROM node:20-alpine AS frontend
WORKDIR /build
RUN corepack enable && corepack prepare pnpm@10 --activate
COPY frontend/package.json frontend/pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile
COPY frontend/ ./
RUN pnpm run build

# Stage 2: deps (native better-sqlite3)
FROM node:20-slim AS deps
RUN apt-get update && apt-get install -y --no-install-recommends \
    python3 make g++ && rm -rf /var/lib/apt/lists/*
WORKDIR /app
RUN corepack enable && corepack prepare pnpm@10 --activate
COPY server/package.json server/pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile --prod

# Stage 3: runtime
FROM node:20-slim
RUN corepack enable && corepack prepare pnpm@10 --activate
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY server/ ./
COPY --from=frontend /build/dist /app/frontend/dist
RUN mkdir -p /app/data/uploads /app/data/uploads/thumbs && chown -R node:node /app
USER node
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=5s --start-period=20s \
  CMD node -e "fetch('http://localhost:3000/api/providers').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"
```

## Volumes / persistence

| Container path | Host path | Purpose | Mode |
|---|---|---|---|
| `/app/data/chat.db` | `./data/chat.db` | SQLite | rw |
| `/app/data/uploads/` | `./data/uploads/` | Uploads | rw |
| `/models/ggml-medium.bin` | `./models/ggml-medium.bin` | Whisper model | ro |
| `/projects` (в `app`) | `${CONTEXT_BASE_DIR}` — **опционально** | Projects | ro |
| `/root/.ollama` | `ollama-models` (named) | Ollama models | rw |

**`CONTEXT_BASE_DIR`** — **не** в `docker-compose.yml` по умолчанию (пользователь может не хотеть монтировать). Если нужно — **явно**:
```yaml
# docker-compose.override.yml (пользователь создаёт сам)
services:
  app:
    volumes:
      - /home/user/progs:/projects:ro
    environment:
      - CONTEXT_BASE_DIR=/projects
```
**Почему не в основном compose:** `${CONTEXT_BASE_DIR}:/projects` с пустым `CONTEXT_BASE_DIR` → Compose **ошибка** (`invalid mount path`). Пользователь **должен** явно указать путь. README объясняет.

**Windows:** путь `C:/Users/.../progs` (прямые слеши) или WSL2 `/mnt/c/...` (медленно) / `/home/...` (быстро). README.

## Failure modes

| Scenario | Handling |
|---|---|
| Qdrant/whisper не запущен | `503` (существующий fallback) |

## Ограничения и риски (актуализировано)

1. **GPU только Linux + NVIDIA.** macOS (Apple Silicon) — CPU-only. Windows — WSL2 + NVIDIA driver. AMD — не поддерживается.
2. **`host.docker.internal`** — Linux требует `extra_hosts`. macOS/Windows — из коробки.
3. **SQLite на macOS/Windows** — медленно (bind-mount). Linux — ок. Документировать.
4. **Размер образов:** `app` ~1 ГБ, `whisper` (CUDA) ~3 ГБ. Multi-stage + runtime base — обязательно.
5. **Whisper-модель** (~1.5 ГБ) — **не** в образе (volume). README / entrypoint.
6. **`CONTEXT_BASE_DIR`** — не в основном compose (пустой путь → ошибка). Пользователь создаёт `override`.
7. **Windows path** — `C:/...` (прямые слеши). WSL2 — `/mnt/c/...` (медленно).
8. **`.env` с секретами** — не в образе (`.dockerignore`), `env_file` только runtime.
9. **`ollama pull`** — первый pull ~4.7 ГБ, долго. Упомянуть.
10. **Логи** — `json-file` с ротацией (10 МБ × 3), иначе растут.
11. **Non-root** — `USER node` в `app`, `chown` для volumes.
12. **`better-sqlite3` native** — build-stage с `python3 make g++`, runtime — без.

## Итог

- **Микросервисы, не монолит:** `app` + `whisper` (+ `ollama` profile).
- **GPU:** `runtime: nvidia` (не `deploy.resources`).
- **`extra_hosts`** для Linux.
- **`env_file`** (не `.env` в образе).
- **`healthcheck`** для всех.
- **Два Dockerfile** (`app`, `whisper`), CPU-only через `ARG USE_CUDA=false`.
- **`CONTEXT_BASE_DIR`** — через `docker-compose.override.yml` (пользователь явно).
- **README** — Prerequisites (NVIDIA Toolkit), Quick Start, Troubleshooting, Windows path.

**Это снимает барьер входа для опенсорса** — одна команда `docker compose up -d` (или с `--profile ollama`), без Node.js, pnpm, компиляции whisper на хосте. GPU — опционально (CPU fallback). **Готово к сохранению.**

## Краткий ответ на «стоит ли»

**Да, стоит** — Docker-инфраструктура **критична** для опенсорс-проекта (снимает барьер входа). Но **не в том виде, как в исходном плане**:
- **Монолит** → **микросервисы** (проект уже микросервисный по архитектуре).
- **`deploy.resources`** → **`runtime: nvidia`** (работает в `compose up`).
- **`host.docker.internal`** → **`extra_hosts`** в compose (не только README).
- **Один Dockerfile** → **два** (`app`, `whisper`).
- **Entrypoint с `&`** → **отдельные контейнеры**.
- **`depends_on: ollama`** → **убрать** (опциональный).
- **`CONTEXT_BASE_DIR`** → **`override.yml`** (не в основном, иначе ошибка на пустом пути).

С этими исправлениями — **готовый план**, можно сохранять. Оценка: **~5–7 дней** (два Dockerfile, compose, README, тесты на Linux/macOS/Windows/WSL2). **Окупается** для опенсорса.
