# Оценка трёх направлений: streaming, reasoning в ответе, мульти-репо RAG + Docker-влияние

Ниже — по каждому пункту отдельно, с оценкой «вложения — выгода — риски», затем сводка.

---

## 1. Streaming — отдельный трек, оценка

### 1.1. Проблема подтверждена — и она реальная

Сейчас `/api/chat` **не streaming**: `provider.chat({ stream: false })` возвращает **весь** ответ одним JSON. Пользователь ждёт **полное** время генерации:
- Короткий ответ (200 токенов, 35B на GPU) — **~3–5 с** — терпимо.
- Длинный ответ (2000 токенов) — **~30–40 с** — **боль**.
- Reasoning-модель (Qwen3.8, 9901 токенов размышлений из инцидента answer-loss-diagnostics) — **~2–3 минуты** — пользователь думает, что приложение зависло.
- **RAG с большим контекстом** (P2, 32K промпт) — **TTFT** (time-to-first-token) сам по себе 3–10 с (обработка промпта), а потом ещё генерация.

**Streaming закрывает именно это:** TTFT сокращается до времени обработки промпта (3–10 с), дальше токены идут в UI по мере генерации. Пользователь **читает** ответ, пока модель **дописывает**. Для длинных ответов — **субъективное** ускорение в 5–10 раз (не реальное, но UX-скачок).

### 1.2. Что уже есть в коде (важно для оценки)

- **`LlamaCppProvider.chat`** — **уже есть** streaming-ветка (`if (stream && response.body)`): SSE-парсер, буферизация строк, `delta.content` + `delta.reasoning_content`, `finish_reason`, `lastMetrics`. Она **переписана** в answer-loss-diagnostics и **работает**.
- **`OllamaProvider.chat`** — **уже есть** streaming-ветка (но **проще**: `chunk.split('\n')` без буферизации — **баг** для разрезанных чанков, надо чинить).
- **`aiHelperController.generateHint`** — **уже стримит** токены через **WebSocket** (`hint_token` / `hint_done`). Это **готовый паттерн** для `/api/chat`.
- **`chatController`** — **не** использует `stream: true`, всегда `stream: false`.

**Вывод:** **бэкенд-часть streaming уже на 80% готова** (провайдеры умеют, WebSocket-паттерн есть). Не хватает:
1. **Транспорт** от провайдера до браузера: SSE (Server-Sent Events) на `/api/chat` **или** WebSocket (как `aiHelper`).
2. **`chatController`** — `stream: true`, проброс чанков.
3. **Фронт** — `fetch` + `ReadableStream` (SSE) или WebSocket-клиент, инкрементальный рендер markdown.
4. **Сохранение в БД** — **после** завершения стрима (сейчас `addMessage` вызывается один раз с полным ответом; при streaming — накапливать в буфер, сохранять в конце).
5. **Метрики** — `lastMetrics` из финального чанка (уже есть в провайдере).
6. **Ошибки mid-stream** — если провайдер упал на 50% — что показать? (частичный ответ + маркер обрыва — паттерн `composeAssistantAnswer` уже есть).

### 1.3. Транспорт: SSE vs WebSocket

| Критерий | SSE (`/api/chat` → `text/event-stream`) | WebSocket (`/ws/chat`) |
|---|---|---|
| Сложность бэкенда | Низкая (`res.write('data: ...\n\n')`) | Средняя (уже есть `aiHelperWs` — можно переиспользовать) |
| Сложность фронта | Низкая (`fetch` + `ReadableStream`) | Средняя (`WebSocket` + reconnect) |
| Совместимость с существующим `/api/chat` | Высокая (тот же путь, `Accept: text/event-stream`) | Низкая (новый путь, новый контракт) |
| Реконнект при обрыве | Автоматический (EventSource) — но `fetch`-based SSE — **ручной** | Ручной (уже есть в `aiHelperSocket.ts`) |
| Прокси/nginx | Может буферизовать (нужен `X-Accel-Buffering: no`) | Прозрачно |
| `FormData` (файлы) | **Не поддерживается** SSE-клиентом (`EventSource` — GET only). Нужен `fetch` + POST + `ReadableStream` | **Поддерживается** (WebSocket + отдельный POST для файлов, или бинарный WS) |

**Ключевая проблема SSE + текущий `/api/chat`:** `/api/chat` — **POST multipart** (файлы, `FormData`). `EventSource` умеет только GET. **`fetch` + POST + `ReadableStream`** — работает, но это **не** «нативный SSE», а ручной парсинг. Ок, но чуть сложнее.

**WebSocket** — `aiHelperWs` уже есть, паттерн `hint_token`/`hint_done` — **готов**. Но `/api/chat` — multipart (файлы); WebSocket бинарные файлы — отдельная история. **Гибрид:** файлы — через существующий POST (как сейчас), ответ — через WebSocket (по `questionId`).

**Рекомендация:** **SSE через `fetch` + POST + `ReadableStream`**:
- `/api/chat` остаётся POST multipart, но при `Accept: text/event-stream` — отвечает SSE-потоком.
- Фронт: `fetch('/api/chat', { method: 'POST', body: formData, headers: { Accept: 'text/event-stream' } })` → `response.body.getReader()` → парсинг `data: {...}\n\n`.
- **Один** эндпоинт, **один** контракт (JSON vs SSE — по `Accept`), **без** нового WebSocket.
- Реконнект — **не** автоматический (как и сейчас; при обрыве — ошибка + `failedText` в композер, паттерн уже есть).

**Альтернатива WebSocket** — если хочется переиспользовать `aiHelperSocket` (reconnect, статус). Но `/api/chat` — multipart, а WS — текстовый; придётся **два** канала (POST для файлов + WS для ответа) — сложнее. **SSE проще.**

### 1.4. Оценка

| Компонент | Время |
|---|---|
| `chatController` — `stream: true`, накопление, сохранение в конце, ошибки mid-stream | ~1 день |
| `apiGateway.chat.sendStream` (fetch + ReadableStream + SSE-парсер) | ~0.5 дня |
| `chat-area.tsx` — инкрементальный рендер (буфер + `ReactMarkdown` на каждом чанке — **дорого**; throttle до 50–100 мс) | ~1.5 дня |
| `OllamaProvider` — **починить** SSE-парсер (буферизация, как в llama.cpp) | ~0.5 дня |
| Обработка ошибок mid-stream (частичный ответ + маркер, `failedText`) | ~0.5 дня |
| Метрики (TTFT из первого чанка, TPS из финального) | ~0.5 дня |
| Тесты (SSE-парсер, обрыв, пустой поток) | ~1 день |
| **Итого** | **~5.5–6 дней** |

### 1.5. Выгода и риски

**Выгода:** **высокая** для длинных ответов и reasoning-моделей. UX-скачок: пользователь **видит** прогресс, не думает «зависло». TTFT 3–10 с вместо 30–180 с.

**Риски:**
- **Инкрементальный markdown-рендер** — дорого (перепарсинг всего текста на каждом чанке). **Throttle** до 50–100 мс обязателен, иначе CPU-жор в браузере.
- **Незакрытые code fences** в середине стрима — `ReactMarkdown` может падать/ломаться. Решение: **не** парсить markdown в процессе, показывать **plain text** с мигающим курсором; финальный рендер — после `done`. (Cursor/Open WebUI так и делают.)
- **Сохранение в БД** — только **после** `done`. Если пользователь закрыл вкладку mid-stream — ответ **потерян** (сейчас — тоже, но там JSON атомарный). Решение: сохранять **накопленный** буфер на `close` (частичный ответ + маркер).
- **Метрики** `inputTokens`/`outputTokens` — из финального чанка (usage), у llama.cpp — ок; у Ollama — `done: true` чанк.
- **`reasoning_content`** — при streaming reasoning идёт **до** content (Qwen3.8). UI должен **разделять** (см. п.2).

**Вердикт:** **стоит**, но **отдельным треком** (не смешивать с P0.1/P0.2/P1.2/P2). **~6 дней**, высокая выгода. **Обязательное условие:** throttle рендера + plain-text в процессе + финальный markdown.

## 2. Reasoning в ответе — включать блок, показывать обрезку

### 2.1. Проблема подтверждена

**Инцидент answer-loss-diagnostics** (2026-11-12): Qwen3.8 потратила **9901 токенов** на reasoning, контекст (16384) кончился до видимого ответа, `finish_reason=length`, `content=''`, `reasoning_content` — **9901 токенов**. Приложение **читало только `content`** → в чате **пустой ответ** без объяснения. Пользователь **не знал**, что модель «думала» 2–3 минуты и **обрезалась**.

**Что уже сделано** (в коде, PR answer-loss-diagnostics):
- `composeAssistantAnswer` — если `content=''` и `reasoning` есть → **статусный маркер** + **начало** reasoning (1200 символов) в `content`. Полные размышления — **в логах** (`log.warn`).
- `metrics.reasoningChars` / `reasoningPreview` — в БД (1000 символов).
- `finishReason='length'` → `truncated=true` → маркер обрыва в `content`.

**Что НЕ сделано:** отдельный **блок reasoning** в UI (раскрывающийся, как в ChatGPT/DeepSeek). Сейчас reasoning **теряется** (только 1200 символов в маркере, полные — в логах сервера, пользователь их **не видит**).

### 2.2. Что предлагается

**Включать в ответ блок reasoning** (если есть) — **отдельно** от `content`, **раскрывающийся** в UI:
- `content` — видимый ответ.
- `reasoning` — «Thinking…» (свёрнут по умолчанию, разворачивается по клику).
- **Если reasoning обрезан** (контекст кончился) — **явно** показать: «[Reasoning truncated: 9901/9901 tokens, context limit reached]».

### 2.3. Что уже есть / чего не хватает

| Есть | Не хватает |
|---|---|
| `LlamaCppProvider.chat` возвращает `reasoning` (и в stream, и в non-stream) | `chatController` **не сохраняет** `reasoning` в `messages` (только `reasoningPreview` 1000 символов при `reasoningSaved`) |
| `composeAssistantAnswer` — маркер при `content=''` | UI **не рендерит** `reasoning` отдельным блоком |
| `metrics.reasoningChars` / `reasoningPreview` | Нет поля `messages.reasoning` (полный текст) |
| `finishReason='length'` → `truncated` | UI **не показывает** «reasoning truncated» явно (только общий маркер) |

### 2.4. Оценка

| Компонент | Время |
|---|---|
| **Схема БД:** `messages.reasoning TEXT` (nullable) — миграция `ensureColumns` | ~0.5 дня |
| **`chatController`:** сохранять `result.reasoning` в `messages.reasoning` (не только preview); для stream — накапливать | ~1 день |
| **`composeAssistantAnswer`:** не терять reasoning (сохранять полностью в БД, маркер — как сейчас) | ~0.5 дня |
| **UI:** компонент `ReasoningBlock` (свёрнут/развёрнут, «Thinking…», счётчик токенов, маркер обрезки) | ~1.5 дня |
| **UI:** интеграция в `chat-area.tsx` (под ответом, перед/после `content`) | ~0.5 дня |
| **UI:** при streaming — reasoning идёт **до** content, показать «Thinking…» **до** первого токена content | ~1 день (если streaming) / 0 (если non-stream) |
| **Copy Q&A** — включать ли reasoning? (решение: **опционально**, чекбокс) | ~0.5 дня |
| **Тесты** | ~0.5 дня |
| **Итого (без streaming)** | **~4–4.5 дня** |
| **Итого (со streaming, интеграция)** | **~5–5.5 дней** |

### 2.5. Выгода и риски

**Выгода:** **высокая** для reasoning-моделей (Qwen3.8, DeepSeek-R1, o1-like):
- Пользователь **видит**, что модель «думала» — доверие к ответу.
- При обрезке — **явно** видно, **где** и **почему** (контекст), а не «пустой ответ».
- Можно **скопировать** reasoning (для отладки, для понимания логики).
- **Восстановление после F5** — reasoning в БД, не только в логах.

**Риски:**
- **Объём БД:** reasoning — 10–35 КБ на сообщение (9901 токенов ≈ 35 КБ). На 1000 сообщений — 35 МБ. **Терпимо**, но надо **не** инжектить в промпт (иначе раздувает контекст — **не** включать reasoning в `[Ранее]`; только в UI).
- **Copy Q&A** — если включать reasoning, копируется 35 КБ. **Опционально** (чекбокс «Include reasoning»).
- **Streaming + reasoning** — reasoning идёт **до** content; UI должен **сначала** показать «Thinking…» (раскрытый или свёрнутый?), **потом** content. **Свёрнутый** по умолчанию — правильно (не отвлекает).
- **Приватность** — reasoning может содержать **черновики** (не отредактированные мысли). Пользователь должен **понимать** (свёрнут, но доступен). Для локального приложения — не проблема, но пометить «internal» в UI.

**Вердикт:** **стоит**, **~4–5 дней**, высокая выгода. **Обязательное условие:** reasoning **не** инжектить в промпт (только в UI/БД), **не** включать в `[Ранее]`. С streaming — **сначала** «Thinking…», **потом** content.

## 3. Мульти-репо RAG — это **другая парадигма**, не «расширение PROJECT»

### 3.1. Проблема подтверждена — и она **реальная боль**

**Сценарий владельца:**
- **5 репозиториев**, все **взаимосвязаны** (протокол, веб-сайт, SDK, документация, тесты).
- Правка в **протоколе** → требует правки в **веб-сайте** (API, UI).
- Контекст **в каждом** — сотни–тысячи файлов. **Вручную** attach — **невозможно** (`MAX_REFERENCE_FILES=100`, а файлов 1000+).
- Сейчас PROJECT mode — **один** проект на сессию. Переключение — **теряется** контекст другого.

**Это ровно тот кейс, где RAG **окупается**:**
- Semantic search **по всем 5** репо сразу — «найди, где `registerWalletAdapter` используется в протоколе и веб-сайте».
- Один вопрос — фрагменты из **разных** репо.
- Индексация **в фоне** — все 5, параллельно.

### 3.2. Что предлагается (переформулировано)

**Не «расширение PROJECT»**, а **новая парадигма**:

1. **PROJECT mode → переименовать в FILES** (текущий: один проект, attach файлов, mtime-кэш). Семантика «работа с файлами одного проекта» — **правильная**, но имя «Project» **конфликтует** с «workspace». **FILES** — точнее.
2. **Новый режим RAG / PROJECTS (или WORKSPACE)**:
   - **Workspace** — **набор** репозиториев (1–5+), с **именем** (`my-product`).
   - **Индексация** — **параллельно**, в фоне (5 репо × 1000 файлов = 5000 файлов, ~10–20 мин; **не** блокирует UI).
   - **Единый поиск** — по **всем** репо в workspace (фильтр `workspace_id` в Qdrant, или `project_path IN [...]`).
   - **UI:** кнопка «Re-index workspace» (актуализация индексации — как в п.3.1 запроса).
3. **Qdrant:** коллекция `code_snippets`, фильтр по `workspace_id` (или `project_path` ∈ список). **Одна** коллекция — **проще**, чем per-workspace.
4. **БД:** таблица `workspaces` (`id`, `name`) + `workspace_projects` (`workspace_id`, `project_id`). `sessions.workspace_id` (nullable — если `mode='rag'`).

### 3.3. Почему это **не** «расширение PROJECT»

| Аспект | PROJECT (FILES) | WORKSPACE (RAG) |
|---|---|---|
| Единица | Один проект | **Набор** проектов |
| Attach | Вручную, `MAX_REFERENCE_FILES=100` | **Не нужен** (RAG находит сам) |
| Контекст | mtime-кэш, полные файлы | Semantic search, фрагменты |
| Индексация | Не нужна (mtime) | **Нужна** (Qdrant, фон) |
| Масштаб | 10–100 файлов | **1000–5000+** файлов |
| Вопрос | «Проанализируй этот файл» | «Где `X` используется в **протоколе и сайте**?» |
| `[Материалы]` | Attached files | **RAG-фрагменты** (из всех репо) |

**Это два разных режима**, не «расширение одного». PROJECT (FILES) — **остаётся** (attach, mtime, малые проекты). WORKSPACE (RAG) — **новый** (мульти-репо, semantic, большие объёмы). **Оба** — в UI (ModeToggle: `Research / Files / Workspace`).

### 3.4. Что меняется в плане P2 (актуализация)

**Было (P2 в текущем виде):** «RAG-слой поверх PROJECT mode» — один проект, `projects.path`, `[Релевантные фрагменты]` в `[Материалы]`.

**Стало (с учётом мульти-репо):**
- **PROJECT → FILES** (переименование, семантика та же: attach, mtime).
- **Новый WORKSPACE mode:**
  - `workspaces` (`id`, `name`, `created_at`).
  - `workspace_projects` (`workspace_id`, `project_id`, `added_at`).
  - `sessions.workspace_id` (nullable).
  - Qdrant: `code_snippets` с `project_path` (как было), поиск — `project_path IN (workspace.project_paths)`.
  - Индексация — **все** репо workspace, **параллельно** (`p-limit(5)`), **фон** (не блокирует UI).
  - UI: `WorkspacePanel` (список репо, статус индексации каждого, кнопка «Re-index all»).
  - `[Релевантные фрагменты]` — из **всех** репо, с указанием `repo:file:line`.
  - **RAG-бюджет** — от `retainPercent` (D3), но фрагменты **из разных** репо — сортировка по релевантности (не по репо).

### 3.5. Оценка (дополнительно к P2 MVP)

**P2 MVP** (один проект, semantic, инкрементальная) — **~11–15 дней** (из предыдущего плана).

**Дополнительно для WORKSPACE:**

| Компонент | Время |
|---|---|
| БД: `workspaces`, `workspace_projects`, `sessions.workspace_id` + миграции | ~1 день |
| `workspaceService.js` (CRUD, attach/detach repo) | ~1 день |
| Индексация **параллельно** (`p-limit`, фон, прогресс) | ~1.5 дня |
| Qdrant-поиск по `project_path IN [...]` (фильтр `any`) | ~0.5 дня |
| `workspaceRoutes` + `workspaceController` | ~1 день |
| UI: `WorkspacePanel` (список репо, статусы, Re-index) | ~2 дня |
| UI: ModeToggle `Research / Files / Workspace` | ~0.5 дня |
| `buildLLMContext` — `[Релевантные фрагменты]` из **всех** репо (с `repo:` префиксом) | ~0.5 дня |
| Тесты (мульти-репо поиск, параллельная индексация) | ~1.5 дня |
| **Итого WORKSPACE** | **~9.5–10.5 дней** |

**Полный P2 (MVP + WORKSPACE):** **~20–25 дней** (было ~11–15 для одного проекта). **Существенно дороже**, но **ровно та боль**, которую описал владелец.

### 3.6. Выгода и риски

**Выгода:** **очень высокая** — это **та самая** боль:
- «Где `registerWalletAdapter` используется в протоколе и сайте?» — **один** вопрос, **оба** репо.
- «Обнови протокол — что ещё сломается в веб-сайте?» — RAG находит **связи** между репо.
- 5 репо × 1000 файлов — **не** attach вручную, RAG **сам**.
- **Параллельная** индексация — 5 репо за ~10–20 мин (в фоне), не блокирует.

**Риски:**
- **Дорого** (~10 дней дополнительно) — но **окупается**, если 5 репо — реальный workflow.
- **Параллельная индексация** — 5 × embedding llama.cpp **одновременно** — **нагрузка на CPU** (RAM-модель). Нужен `p-limit(2–3)`, не 5. Или — **последовательно** (медленнее, но стабильнее). **Зафиксировать.**
- **Qdrant-фильтр** `project_path IN [...]` — **работает** (`match: { any: [...] }`), но **дороже** одного `match: { value }`. На 5 репо × 1000 файлов × 10 чанков = 50K векторов — **ок** (Qdrant держит миллионы).
- **UI-сложность** — `WorkspacePanel` + `RepoPanel` (per-repo статус) — **+2 дня**. Но **необходимо** для UX.
- **Конфликт имён** — `WORKSPACE` vs `PROJECTS` vs `RAG`. **Зафиксировать:** режим называется **Workspace** (UI), `mode='workspace'` (БД), `workspaces` (таблица). `PROJECT` → `FILES` (`mode='files'`, таблица `projects` **остаётся** — `projects` = репозиторий, `workspaces` = набор).

**Вердикт:** **стоит**, но это **отдельный трек** (не «расширение P2»), **~10 дней** дополнительно, **окупается** для реального мульти-репо workflow. **Ключевое:** переименовать PROJECT → FILES, новый WORKSPACE — **не** «расширение PROJECT», а **новая парадигма**.

## 4. Docker — насколько упадёт скорость ответа и TPS

### 4.1. Короткий ответ

**Практически не упадёт** — **если** LLM и embedding **вне** Docker (на хосте, как сейчас). Docker добавляет **сетевой хоп** (app → host:8080), но:
- **localhost / host.docker.internal** — **<1 мс** overhead (loopback / bridge).
- **HTTP overhead** — **<1 мс** на запрос (заголовки, парсинг).
- **TPS** (генерация токенов) — **не зависит** от Docker (модель на GPU хоста, inference на хосте).

**Упадёт**, если **LLM в Docker** (Ollama profile):
- **GPU-проброс** — **~1–5%** overhead (NVIDIA Container Toolkit, PCIe passthrough). На практике — **незаметно** (60–85 t/s → 58–82 t/s).
- **Модель в volume** — **первая** загрузка в RAM/VRAM **+1–2 с** (чтение с диска через volume), дальше — **в памяти**, без разницы.

**Упадёт сильнее**, если **всё в одном контейнере** (монолит, **отвергнут** в P1.2):
- Node.js + whisper + LLM в одном контейнере — **CPU contention** (Node.js event loop vs whisper CPU vs LLM CPU-offload) → **TPS падает** на 10–30%.
- **Не** наш случай (микросервисы).

### 4.2. По компонентам

| Компонент | В Docker | Overhead | Комментарий |
|---|---|---|---|
| **LLM inference** (llama.cpp на хосте) | Вне Docker | **0%** | GPU хоста, inference хоста |
| **LLM inference** (Ollama в Docker) | В Docker | **~1–5%** TPS | GPU passthrough, PCIe — минимально |
| **Embedding** (llama.cpp на хосте) | Вне Docker | **0%** | CPU хоста |
| **Embedding** (llama.cpp в Docker) | В Docker | **~1–3%** | CPU passthrough (без GPU) |
| **Whisper** (в Docker) | В Docker | **~1–5%** | GPU passthrough |
| **SQLite** (bind-mount на Linux) | В Docker | **~1–2%** | Нативно (overlayfs) |
| **SQLite** (bind-mount на macOS/Windows) | В Docker | **~50–90%** (медленнее) | virtiofs/gRPC FUSE — **боль** |
| **HTTP** (app → LLM) | В Docker | **<1 мс** | loopback/bridge |
| **Frontend static** (nginx) | В Docker | **0%** | Отдача статики — не критично |

### 4.3. Реальные цифры (оценка)

**Сценарий 1 (рекомендуемый): LLM на хосте, app + whisper в Docker**
- TPS: **60–85 t/s** (как сейчас) — **0%** overhead.
- TTFT: **3–10 с** (обработка промпта на GPU хоста) — **0%**.
- HTTP overhead: **<1 мс** — **незаметно**.
- **Итог:** **скорость не падает**.

**Сценарий 2: Ollama в Docker (profile)**
- TPS: **60–85 → 58–82 t/s** (**−2–3%**).
- TTFT: **3–10 → 3.1–10.2 с** (**+1–2%**).
- **Итог:** **незаметно** для пользователя.

**Сценарий 3: SQLite на macOS/Windows (bind-mount)**
- Запись `chat.db` — **в 5–10 раз медленнее** (virtiofs).
- **Влияние на TPS:** **0%** (SQLite — не в горячем пути генерации; запись `addMessage` — после ответа, ~10–50 мс вместо ~5 мс).
- **Влияние на UX:** **заметно** при частых операциях (список сессий, поиск) — **не** при генерации.
- **Итог:** TPS **не падает**, UX — **чуть** медленнее на macOS/Windows. Linux — **0%**.

**Сценарий 4: Всё в одном контейнере (монолит, отвергнут)**
- CPU contention → TPS **−10–30%**.
- **Не** наш случай (микросервисы в P1.2).

### 4.4. Что **влияет** на скорость (не Docker)

- **Модель** (35B vs 7B) — **основной** фактор.
- **GPU** (RTX 3060 vs 4090) — **основной** фактор.
- **Контекст** (32K vs 8K) — TTFT **линейно** растёт.
- **Reasoning** (Qwen3.8) — **+2–3 мин** на ответ (9901 токенов размышлений).
- **RAG** (P2) — **+TTFT** (обработка 32K промпта вместо 8K) — **+2–5 с** TTFT.
- **Streaming** — **субъективно** ускоряет (TTFT виден, дальше токены идут).

**Docker — не фактор** (при микросервисах + LLM на хосте).

### 4.5. Вывод

**Docker не влияет на TPS** (LLM на хосте) или влияет **незаметно** (Ollama в Docker, −2–3%). **SQLite на macOS/Windows** — медленнее, но **не** в горячем пути генерации. **Микросервисы** (P1.2) — **правильно** (монолит — **−10–30%** TPS).

**Единственное реальное влияние:** **RAG (P2)** — **+2–5 с TTFT** (обработка большего промпта). **Streaming** — **субъективно** компенсирует.
