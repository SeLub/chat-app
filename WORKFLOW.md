# WORKFLOW — регламент совместной работы над репозиторием

**Проект:** `SeLub/chat-app`
**Участники:** SeLub (Заказчик) ⇄ агент-исполнитель (ветки фаз `tz/phase-*`)
**Версия:** 1.2 от 2026-11-08
**Статус:** согласование — правки вносятся по договорённости, версия обновляется
**История:** v1.2 — ветка на каждую фазу (`tz/phase-<x>`), ветка `qwen` закрыта; v1.1 — PR на каждую фазу; v1.0 — исходный регламент

---

## 1. Роли и ответственность

| Роль | Кто | Зона ответственности |
|------|-----|----------------------|
| Заказчик | SeLub | Постановка задач (ТЗ), принятие решений, проверка фаз и PR, merge |
| Исполнитель | агент (работает в ветках фаз `tz/phase-*`) | Анализ, варианты решения, реализация по фазам, ведение worklog, PR, фиксы |

## 2. Рабочее пространство

- **Каждая фаза — в отдельной ветке** `tz/phase-<буква фазы>` (например `tz/phase-b`), отпочкованной от актуального `main`.
- Ветка `qwen` закрыта и удалена (решение Заказчика от 2026-11-08; Фаза A ушла в `main` через PR #2).
- Прямые пуши в основную ветку запрещены. **Merge выполняет только Заказчик.** После merge ветка фазы удаляется (удаливший merge — Заказчик; Исполнитель удаляет ветку по поручению).
- Документы регламента лежат в корне репозитория:
  - `WORKFLOW.md` — этот документ (правила и процесс);
  - `WORKLOG.md` — журнал решений, фаз и статусов (ведёт Исполнитель);
  - `BACKLOG.md` — задачи вне текущего трека (берутся в работу только по прямому указанию Заказчика).

## 3. Цикл работы над задачей

### Фаза 0. Постановка задачи
Заказчик предоставляет ТЗ. Если ТЗ нет — Исполнитель сам предлагает план решения на утверждение Заказчику.

### Фаза 1. Анализ *(Исполнитель)*
Изучает код и ТЗ, возвращает в чат:
- понимание задачи и ограничения;
- вопросы и риски;
- 1–3 варианта решения (плюсы/минусы, трудозатраты);
- свою рекомендацию.

### Фаза 2. Обсуждение и фиксация решений *(Заказчик + Исполнитель)*
- Обсуждаем варианты в чате.
- Принятые решения Исполнитель фиксирует в `WORKLOG.md` (решение + обоснование).
- Фиксация в worklog = «решения утверждены, можно кодить».

### Фаза 3. Исполнение по фазам *(Исполнитель)*
- Задача делится на фазы (небольшая задача = одна фаза).
- Каждая фаза: атомарные коммиты в ветку фазы + запись в `WORKLOG.md` (что сделано, как проверить).
- Каждая фаза завершается открытием PR (см. Фазу 5) — следующая фаза не начинается, пока по PR текущей не принято решение.

### Фаза 4. Фиксы *(Исполнитель)*
- Правки по замечаниям: новые коммиты в ветку фазы, обновление worklog.
- Цикл «проверка → фикс» повторяется до одобрения.

### Фаза 5. Pull Request — на каждую фазу *(Исполнитель)*
- **По завершении каждой фазы** Исполнитель открывает PR из ветки фазы (`tz/phase-<x>`) в `main`.
- До решения Заказчика по PR следующая фаза не исполняется.
- Описание PR: что и зачем изменено, как проверялось (гейты), связь с записью worklog.

### Фаза 6. Ревью PR и merge *(Заказчик)*
- Заказчик ревьюит PR на GitHub; вердикт: **merge** либо **фикс**.
- При замечаниях — возврат в Фазу 4: новые коммиты в ветку фазы автоматически обновляют открытый PR.
- **Merge делает Заказчик.** После merge Исполнитель фиксирует в `WORKLOG.md` статус фазы: `merged`, переключается на `main`, удаляет локальную ветку фазы и начинает следующую фазу от свежего `main`.
- При отклонении — статус `отклонено` / `отложено`.

## 4. Правила ведения WORKLOG.md

- Запись на задачу: `## ГГГГ-ММ-ДД — <название задачи>`, внутри: контекст → решения (с обоснованием) → фазы/статусы → итог.
- Существенное решение: сначала обсуждение в чате, потом фиксация в worklog, потом код.
- Worklog — единственный источник правды «почему сделали именно так».

## 5. Технические правила

- Коммиты: маленькие и атомарные, сообщения в формате `type: описание` (`feat`, `fix`, `docs`, `refactor`, `test`); внутри трека по ТЗ — `TZ-<фаза>.<пункт>: описание`.
- **Перед каждым push: `git pull --rebase`** — дивергенция веток нормальна при параллельной работе (Заказчик и Исполнитель коммитят в одну ветку); при конфликте rebase прерывается без потери данных (`git rebase --abort`), force-push не используется.
- Секреты (токены, ключи, пароли) не попадают в код, коммиты и PR.
- Force-push в ветки фаз — только по явному согласованию с Заказчиком.
- Токен доступа хранится только в песочнице Исполнителя, в файлах репозитория не сохраняется. После сессии Заказчику рекомендуется отозвать/ротировать токен.

## 6. Статусная модель задачи

`новая → анализ → обсуждение → в работе → PR фазы → ревью → (фикс → ревью)* → merged | отклонено | отложено`
