**Версия:** 2.0 (учтены решения U1–U18 по факту фронтенда)
**Статус:** готово к реализации
**Область:** backend (`generationParams`, `chatController`, `LlamaCppProvider`, `OllamaProvider`, `chatRoutes`), frontend (`generationParamsStore`, `generationParams` const, модалка, футер, `apiGateway`, `sessionStore`)
**Связанный документ:** `📌 Задача P0.1 — Динамические параметры генерации.txt`

---

## 1. Цель и границы

### 1.1. Что решаем
Параметры генерации (`temperature`, `top_p`, `top_k`, `min_p`, `n_predict`, `presence_penalty`, `repeat_penalty`) сейчас зашиты в bash-скрипт запуска `llama-server` и в код провайдеров (`temperature: 0.7`). Изменение требует перезапуска сервера. Нужно менять их **на лету, для каждого сообщения**, не трогая llama-server.

### 1.2. Что НЕ входит в scope
Статические параметры llama-server, задаваемые только при запуске, **остаются в bash-скрипте** и через API не меняются:
`--ctx-size`, `--n-gpu-layers`, `--cache-type-k`, `--cache-type-v`, `--flash-attn`, `--spec-type`, `--mlock`, `--threads`, `--batch-size` и т.п.

**Метод `generate()` провайдеров не трогаем** (не вызывается из чата; захардкоженный `temperature: 0.7` в нём остаётся — отдельная задача при необходимости). Меняется только `chat()`.

### 1.3. Ключевой принцип
**«Не передан — не отправляем»**. Если параметр отсутствует в запросе (или `undefined`), приложение не включает его в тело JSON к провайдеру — сервер использует своё дефолтное значение из bash-скрипта. Это касается:
- бэкенда — `chatController` не подставляет дефолты;
- провайдеров — не шлют захардкоженный `temperature: 0.7`;
- фронта — `Reset to Server Defaults` очищает параметры.

## 2. Контракт параметров (единый словарь)

| Параметр | Тип | Диапазон | Семантика |
|---|---|---|---|
| `temperature` | number | 0.0 … 2.0 | Креативность. 0 — детерминизм |
| `top_p` | number | 0.0 … 1.0 | Nucleus sampling |
| `top_k` | integer | 0 … 200 | Top-K. 0 = отключён (llama.cpp) |
| `min_p` | number | 0.0 … 1.0 | Min-P sampling |
| `n_predict` | integer | -1 … 32768 | Лимит токенов ответа. -1 = до стопа по контексту (осознанный выбор пользователя, **не** серверный `--n-predict` по умолчанию). **0 не допускается** |
| `presence_penalty` | number | -2.0 … 2.0 | Штраф за присутствие токена |
| `repeat_penalty` | number | 0.0 … 2.0 | Штраф за повтор. 1.0 = нейтрально |

**Общие правила валидации:**
- Не передан, `null`, `undefined`, пустая строка → параметр отсутствует (не валидируется, не отправляется).
- Не число / `NaN` / `Infinity` → 400 с `code: 'invalid_generation_param'`.
- Вне диапазона → 400 с `code: 'invalid_generation_param'` + `field`, `value`, `min`, `max`.
- Дробные для integer-полей (`top_k`, `n_predict`) → 400 (строгая проверка `Number.isInteger`).
- `n_predict === 0` → 400.

## 3. Backend

### 3.1. Модуль валидации — новый файл `src/utils/generationParams.js`

Чистая функция, тестируется напрямую (без HTTP).

```js
// src/utils/generationParams.js
export const GENERATION_PARAM_SPECS = {
    temperature:       { type: 'number',  min: 0,   max: 2 },
    top_p:             { type: 'number',  min: 0,   max: 1 },
    top_k:             { type: 'integer', min: 0,   max: 200 },
    min_p:             { type: 'number',  min: 0,   max: 1 },
    n_predict:         { type: 'integer', min: -1,  max: 32768, disallowZero: true },
    presence_penalty:  { type: 'number',  min: -2,  max: 2 },
    repeat_penalty:    { type: 'number',  min: 0,   max: 2 },
};

export const GENERATION_PARAM_KEYS = Object.keys(GENERATION_PARAM_SPECS);

/**
 * @param {Object} raw - сырые значения из req.body (могут быть строками из FormData)
 * @returns {{ ok: true, params: Object } | { ok: false, error: { field, value, min, max, message } }}
 */
export function parseGenerationParams(raw = {}) { ... }
```

**Требования к функции:**
1. Для каждого ключа из `GENERATION_PARAM_SPECS`: если в `raw[key]` пусто/`undefined`/`null`/`''` — пропустить (в `params` не класть).
2. Коэрция: `FormData`-поля приходят строками — приводить через `Number(raw[key])`. Если результат `NaN` — 400.
3. `integer`-поля: `Number.isInteger(n)` обязательно после коэрции.
4. `disallowZero`: `n_predict === 0` → 400.
5. Проверка диапазона включительно.
6. Игнорировать любые ключи вне `GENERATION_PARAM_SPECS` (не пробрасывать в провайдер).
7. Возвращать **только валидные переданные** параметры. Пустой объект — легальный результат (все дефолты сервера).
8. Текст сообщения об ошибке — для тоста на фронте: `"temperature must be a number between 0 and 2"`.

### 3.2. `chatController.js` — приём, валидация, логирование, проброс

**Шаг 1. Извлечение и валидация.**
Внутри существующего `try` в `chatHandler`, **после** проверки `MAX_MESSAGE_CHARS` и **до** `processUrlsFromText` — чтобы не тратить время на сеть/реестр вложений при невалидных параметрах:

```js

    log.warn('Invalid generation params, rejecting', {
        field: gp.error.field,
        value: gp.error.value,
        sessionId: sessionId?.slice(0, 8),
    });
    return res.status(400).json({
        error: `Invalid generation parameter: ${gp.error.message}`,
        code: 'invalid_generation_param',
        field: gp.error.field,
        value: gp.error.value,
        min: gp.error.min,
        max: gp.error.max,
    });
}
const generationParams = gp.params;   // {} если ничего не передано
```

Валидация **не пишет** в `last_send_error` (это не провал отправки — вопрос откатывается фронтом в поле ввода, как при `message_too_long`).

**Шаг 2. Логирование.**
В существующий `log.info('Received message', { model, sessionId, ... })` добавить `generationParams` (объект целиком; пустой `{}` — ок, наблюдаемость «ничего не задано»).

**Шаг 3. Проброс в провайдер — обе ветки:**

- **Vision-ветка:** `req.provider.chat({ model, messages, stream: false, ...generationParams })`.
  Параметры применяются и к vision-запросу — тот же `provider.chat` (llama.cpp / Ollama), sampling применяется на сервере **best effort**: сборки vision-моделей могут часть полей игнорировать — не падаем.
- **Обычная chat-ветка:** `req.provider.chat({ model, messages, stream: false, cache_prompt, n_keep, ...generationParams })`.

**Шаг 4. Контракт 400-ответа** (для фронта):

  "code": "invalid_generation_param",
  "field": "temperature",

**Шаг 5. `req.on('close')` warn** — не меняется.

#### 4.1.2. `frontend/src/stores/generationParamsStore.ts` (новый)

Zustand, **persist** в `localStorage` (ключ `generation-params-v1`). Глобальный на приложение (не привязан к сессии).

```ts
interface GenerationParamsState {
  params: GenerationParams;              // {} = все дефолты сервера
  activePreset: PresetName | null;       // null = Custom / Server
  fieldError: GenerationParamKey | null; // подсветка поля после 400 invalid_generation_param

  setParam(key: GenerationParamKey, value: number | undefined): void;  // undefined → удалить ключ
  applyPreset(name: PresetName): void;
  resetToDefaults(): void;
  setFieldError(field: GenerationParamKey | null): void;
  clearFieldError(): void;
}
```

**Логика:**
- `setParam(key, value)`:
  - `undefined` → удалить ключ из `params`, `activePreset = null`.
  - число → `params[key] = value`, `activePreset = null` (любое ручное изменение сбрасывает пресет), `fieldError = null` (правка поля снимает подсветку).
- `applyPreset(name)`: `params = {...PRESETS[name]}`, `activePreset = name`, `fieldError = null`.
- `resetToDefaults()`: `params = {}`, `activePreset = null`, `fieldError = null`.
- `setFieldError(field)`: `fieldError = field` (вызывается из `sessionStore.sendMessage`/`chat-area` при 400).
- `clearFieldError()`: `fieldError = null`.

**Persist:**
```ts
persist(
  (set, get) => ({ ... }),
  {
    name: 'generation-params-v1',
    partialize: (state) => ({ params: state.params, activePreset: state.activePreset }),
    merge: (persisted, current) => {
      // Валидация при загрузке: sanitizeGenerationParams + восстановление пресета
      const safeParams = sanitizeGenerationParams(persisted?.params);
      const safePreset = persisted?.activePreset && matchPreset(safeParams) === persisted.activePreset
        ? persisted.activePreset
        : null;
      return { ...current, params: safeParams, activePreset: safePreset };
    },
  }
)
```

**При загрузке:** битый `localStorage` (ручная правка) → невалидные ключи/значения отброшены `sanitizeGenerationParams`; `activePreset` восстановлен только если набор `params` совпадает с пресетом.

**Поведение:** вопрос возвращается в композер (единый контракт «при провале ничего не теряется» — как для `context_overflow`), вложения возвращаются, тост с текстом ошибки, `fieldError` подсвечивает поле в модалке (если открыта). **Модалку автоматически не открывать** — пользователь может быть в середине другого действия.

**Не писать** в `last_send_error` — сервер валидацию не персистит.

### 4.4. Vision-ветка на фронте
Отправка картинки идёт тем же `FormData` — `generationParams` добавляются тем же кодом в `chatApi.send`. Специальной обработки не требуется. На бэкенде vision-ветка `chatController` пробрасывает `...generationParams` в `req.provider.chat` (best effort на сервере).

## 6. Тестирование (критерии приёмки)

### 6.1. Юнит-тесты `generationParams.test.js` (backend)
1. Пустой объект → `{ ok: true, params: {} }`.
2. Все 7 валидных значений → `params` содержит все 7.
3. Строковые числа из FormData (`'0.5'`) → коэрция в числа.
4. `temperature: 'abc'` → `ok: false`, `field: 'temperature'`.
5. `temperature: 2.5` → `ok: false`, `min: 0, max: 2`.
6. `top_k: 1.5` → `ok: false` (не integer).
7. `n_predict: 0` → `ok: false` (disallowZero).
8. `n_predict: -1` → `ok: true`.
9. `n_predict: -2` → `ok: false` (ниже min).
10. Лишний ключ `foo: 1` → игнорируется, `params` его не содержит.
11. `null`/`''`/`undefined` значения → пропускаются (не в `params`, не ошибка).

### 6.2. Интеграционные (провайдеры, мок `fetch`)
1. `LlamaCppProvider.chat` без `generationParams` → тело **не содержит** `temperature` (регрессия удалена) и не содержит остальных 6.
2. `LlamaCppProvider.chat({ generationParams: { temperature: 0.2, n_predict: 512 } })` → тело `{ temperature: 0.2, max_tokens: 512 }`.
3. `LlamaCppProvider.chat({ generationParams: { n_predict: 512 }, maxTokens: 100 })` → тело `{ max_tokens: 512 }` (приоритет `n_predict`, U15).
4. `OllamaProvider.chat({ generationParams: { n_predict: 512 } })` → тело `options: { num_predict: 512 }`.
5. `OllamaProvider.chat` без параметров → тело **без поля `options`**.
6. `chatController` с невалидным `temperature` → 400 `invalid_generation_param` **до** создания строк реестра (проверить, что `attachments` пуст, `last_send_error` NULL).

### 6.3. Frontend (юнит)
1. `sanitizeGenerationParams`: битые значения отбрасываются, валидные сохраняются.
2. `matchPreset`: точное совпадение → имя пресета, иначе `null`.
3. `generationParamsStore`: `setParam(undefined)` удаляет ключ и сбрасывает `activePreset`; `applyPreset` ставит оба; `resetToDefaults` чистит всё; `setFieldError`/`clearFieldError`.

### 6.4. Сквозной ручной сценарий
1. Открыть модалку `⚙ Params`, выбрать `Coding` → в кнопке `⚙ Params · Coding`, поля заполнены.
2. Отправить сообщение → в логе сервера `Received message` с `generationParams: { temperature: 0.2, ... }`; ответ с низкой температурой (проверить повторяемость на коротком промпте).
3. Ручное изменение `temperature` → `⚙ Params · Custom`.
4. `Reset to Server Defaults` → поля пусты, `⚙ Params`, `params = {}`; отправка → в логе `generationParams: {}`; ответ с серверными дефолтами.
5. F5 → параметры сохранились (Zustand persist).
6. Установить `temperature=5` через прямой запрос → 400 `invalid_generation_param` с полями; в UI (при открытой модалке) поле подсвечено, тост показывает текст.
7. Vision-запрос с выбранным пресетом → параметры ушли (best effort на сервере).
8. Битый `localStorage` (ручная правка `params`) → после F5 невалидные ключи отброшены, отправка работает.

## 7. Крайние случаи и решения

| Кейс | Решение |
|---|---|
| Фронт прислал `temperature=0` | Валидное значение (детерминизм), не путать с «не передано». `parseGenerationParams` различает `0` и `undefined`. |
| Фронт прислал `top_k=0` | Валидно (llama.cpp: 0 = top_k отключён). |
| `n_predict=-1` | Валидно (до стопа по контексту) — **осознанный выбор пользователя** через UI. Отличается от удалённого `max_tokens: -1` из answer-loss-diagnostics (там приложение **само** навязывало `-1`, перекрывая серверный `--n-predict`). В UI подсказка: `-1 = until context stop (may truncate)`. |
| Провайдер `llama_cpp` не поддерживает `min_p` в старой сборке | llama.cpp принимает `min_p` в OAI-эндпоинте с b3xxx; старые сборки молча игнорируют неизвестные поля — не падаем. |
| Пресет изменён, но пользователь передумал | `Custom` не сбрасывает `params` — только `activePreset`; значения остаются, пока пользователь не нажмёт `Reset` или не изменит поле. |
| Битый `localStorage` | `sanitizeGenerationParams` отбрасывает невалидные ключи/значения; `activePreset` восстанавливается только при точном совпадении `params` с пресетом. |
| `maxTokens` аргумент и `n_predict` одновременно | `n_predict` (из UI) выигрывает; `maxTokens` — легаси-параметр, никем не передаётся в `chatController` после этого ТЗ (U15). |
| Ollama: `options` пуст после маппинга | Поле `options` не включается в тело (Modelfile-дефолты). |
| `llama.cpp`: `cache_prompt`/`n_keep` + параметры | Не конфликтуют; параметры пишутся в те же поля тела. |
| Vision-модель игнорирует часть параметров | Best effort — не падаем, сервер применит что может. |
| `invalid_generation_param` (400) | Тост + `fieldError` в сторе (подсветка в модалке) + возврат текста/файлов в композер (единый контракт «ничего не теряется»). В `last_send_error` не пишется. |
| `generate()` провайдеров | Не трогаем (вне scope); захардкоженный `temperature: 0.7` остаётся — зафиксировать комментарием. |
