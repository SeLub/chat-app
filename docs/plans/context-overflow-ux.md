# ТЗ context-overflow-ux: пре-флайт переполнения контекста + баннер ошибки отправки

**Статус:** исполнено в ветке `feat/context-overflow-ux` → PR в `main`.
**Источник:** отчёт владельца 2026-11-11 — переполнение контекста при отправке PDF 5.4 MB; вердикт владельца: «Делаем №1+2. Не терять вопрос. На фейле возвращать текст в поле ввода».

## Симптом (кейс владельца)

Лог сервера при очередном запросе:

```
400 {"error":{"code":400,"message":"request (3937667 tokens) exceeds the available
context size (98304 tokens), try increasing it","type":"exceed_context_size_error",
"n_prompt_tokens":3937667,"n_ctx":98304}}
```

Вложение — PDF 5.4 MB. В UI — сообщение об ошибке прямо в чате (пара «вопрос-ошибка»); F5 восстанавливает пары из БД, ошибка исчезает, запросы снова работают. Владелец: «Error - F5 как бы не очевиден. И UX сомнительный».

## Корневая причина аномалии 3.9M токенов (≈40× окна)

Проверено по `contextBuilder.js`: char-бюджет `maxChars = contextSize * 4` режет **только Q&A-историю** — `filesContext` (`[Материалы]`, извлечённый текст вложений) входит в промпт **целиком, без обрезки**:

- `fixedChars = sysprompt.length + filesContext.length` может быть `>> maxChars`; тогда `availableChars = max(maxChars - fixedChars, 0) = 0`, история зажимается в пустоту, но файлы всё равно уходят в промпт;
- в RESEARCH-режиме `allFileIds` собирается из `attachments_meta` **всех** сообщений сессии + текущие вложения → извлечённый текст реинжектится в каждый запрос;
- PDF 5.4 MB (текстовые стримы сжаты deflate ~4×) даёт ~15–20 MB извлечённого текста → ~3.9M токенов при окне 98304 → жёсткий 400 от llama.cpp.

То есть это не «честное» переполнение долгим диалогом, а инъекция веса одного документа. Отклонение пре-флайтом (№1) + подсказка в баннере («удали Q&A-пару с файлом / новая сессия») закрывают кейс UX-ом; изменение самой инъекции (кап на `[Материалы]`) — отдельное решение владельца, в этот трек не входило.

## Вторая причина плохого UX — ошибка без чисел и транзитная пара

1. `LlamaCppProvider.chat` парсил тело 400 **только в лог** — фронт получал голый `Chat error: Bad Request`, `n_prompt_tokens`/`n_ctx` терялись.
2. `sessionStore.sendMessage` при любом фейле оставлял оптимистичный user-месседж в чате и добавлял assistant-сообщение с текстом ошибки (`addBotMessage`) — транзитная пара, не в БД: лечилась только F5, вопрос пропадал.

## Решение №1 — серверный пре-флайт (быстрый отказ ДО вызова LLM)

`chatController.chatHandler`, chat-ветка, сразу после сборки контекста. Оценка — та же chars/4-эвристика, что в `buildLLMContext`:

```
estimatedPromptTokens = ceil((fixedChars + actualHistoryChars + questionChars + 64) / 4)
```

Если `estimatedPromptTokens > contextLength` → `400 {error, code:'context_overflow', estimatedTokens, contextLength}` **без** вызова провайдера; строки реестра этой отправки чистятся (`deleteUnclaimedAttachments`, принцип attachment-cascade).

- Преф-флайт ловит именно file-driven переполнение (история по построению влезает в бюджет chars/4, файлы — нет).
- Граница снизу не страдает: обычные запросы проходят как раньше (тест «большой файл при достаточном контексте → 200»).
- Vision-ветку не трогали: base64-картинку токенизирует mmproj, chars/4 неприменим.
- Жёсткий 400 от llama.cpp остаётся второй линией (эвристика chars/4 занижает на кириллице/коде) — для него баннер показывает **реальные числа токенизатора**.

**Проброс чисел.** `LlamaCppProvider.parseLlamaCppErrorResponse(bodyText)` (экспорт, покрыт тестами): обёртка `{error:{…}}` (b4xxx–b6xxx) и плоский JSON разбираются одинаково → `{message, type, n_prompt_tokens, n_ctx}`; не-JSON → null. Ошибка вешается на `err.details`; оба catch chatController (chat + vision) пробрасывают `details` верхним уровнем 500-ответа. Фронт получает их через `ApiError.details` (transport уже был).

## Решение №2 — баннер вместо пары-ошибки, вопрос не теряется

**`frontend/src/lib/sendError.ts` (новый, чистая логика + 12 тестов):**
- `SendErrorInfo { sessionId, kind, title, detail, failedText, failedFiles?, estimatedTokens?, contextLength? }`; kinds: `context_overflow` | `provider_unavailable` | `network` | `server`;
- `buildSendErrorInfo(e, ctx)` — разбор `ApiError.details` (обе формы overflow), 503, status 0, generic, строка `result.error` (legacy-контракт, ECONNREFUSED-текст сохранён), fallback-подсказка про другой провайдер — как раньше;
- `formatTokensCompact` — `3937667 → «3.94M»`, `98304 → «98K»`.

**`sessionStore.ts`:** `sendError`-состояние + `setSendErrorFromException` (сборка баннера + refreshStatus для provider/server как раньше) + `dismissSendError` + `rollbackMessage` (откат оптимистичного сообщения и questionCounter). Все три провальные ветки `sendMessage` (catch / `!result` / `result.error`) больше **не создают** пары-ошибки: откат вопроса + `sendError`. Новая отправка гасит предыдущий баннер (баннер = последняя провальная попытка). Успех баннер не возвращает.

**`chat-area.tsx`:** неблокирующий баннер над композером (только в сессии, где случился фейл — `sendError.sessionId === viewingSessionId`): заголовок, деталь, моно-строка `≈3.94M / 98K tok`, кнопка **«Повторить»** (повторная отправка ИСХОДНОГО текста с исходными файлами) и крестик. Эффект на `activeSendError` возвращает `failedText` в поле ввода (если пользователь не начал печатать новый) и `failedFiles` в композер (если он пуст) — вопрос не теряется даже если баннер закрыли. `handleSend`/`handleRetry` при guard-ошибках (нет сессии/модели) тоже возвращают текст+файлы.

## Что осталось как было (осознанно)

- Транзитность: пара-ошибка никогда не писалась в БД — теперь её нет и в стейте; F5 больше не «способ убрать ошибку», потому что баннер живёт в состоянии и после фейла вопрос уже в поле ввода. Персистентная плашка на сессию (переживает F5) — не делали (вариант №3 из обсуждения).
- Авто-тримминг `[Материалы]` с повтором (вариант №5) — не делали, решение о политике инъекции файлов за владельцем.
- Черновик поля ввода в localStorage (F5 сохранял бы незавершённый текст) — не делали, отдельная тема.

## Ручная проверка (владелец, DoD)

1. Приложить файл, дающий больше окна токенов (кейс владельца — PDF 5.4 MB; тестовый минимум — текст/CSV ~400 KB при ctx 98304) → отправить → в чате НЕТ пары «вопрос-ошибка», над композером баннер «Контекст переполнен» с `≈N / 98K tok`, вопрос — в поле ввода, вложение — в композере.
2. Нажать «Повторить» без правок → баннер появится снова (отказ детерминирован), вопрос/файлы снова в композере.
3. Удалить Q&A-пару с файлом (Delete под вопросом) → «Повторить» → запрос проходит (реестр чистится каскадом, PR #20).
4. Остановить llama-server → отправить → баннер «llama_cpp недоступен» (+ подсказка про Ollama, если подключён); запустить сервер → «Повторить» → успех.
5. Обычный диалог — без баннера, поведение чата как раньше (пары пишутся в БД, F5 восстанавливает).
