# ТЗ send-error-persist-actions: персистентная плашка провальной отправки + быстрые действия

**Статус:** исполнено в ветке `feat/send-error-persist-actions` → PR в `main`.
**Источник:** вердикт владельца 2026-11-11 — «делаем №3+4» (после merge PR #22 `feat/context-overflow-ux`, №1+2 в main).

## Нумерация вариантов (реконструкция)

Исходный нумерованный список UX-вариантов давался владельцу текстом в чат и в репозиторий не попал. В предыдущем ТЗ (`docs/plans/context-overflow-ux.md`, «Что осталось как было») зафиксированы:

- **№3 — «персистентная плашка на сессию (переживает F5)»** — прямая цитата, формулировка не менялась;
- **№5 — «авто-тримминг [Материалы] с повтором»** — в этот трек не входит (политика инъекции файлов — отдельное решение владельца).

**№4 реконструирован** из подсказки транзитного баннера №2 («удали Q&A-пару с этим файлом (Delete под вопросом) или начни новую сессию» — `sendError.ts:78/92`): быстрые действия в плашке, превращающие текстовую подсказку в кнопки одного клика. Связка «№3+№4» одним треком — плашка, которая переживает F5 **и из которой можно разрешить переполнение**. Если владелец подразумевал под №4 иное — правка по факту ревью.

## Что не закрывают №1+2 (дыры после PR #22)

1. **F5 стирает инцидент безвозвратно.** Провальная отправка не оставляет следов: user-месседж в БД не пишется (addMessage — только после успешного ответа LLM, оптимистичный вопрос откатывается), строки реестра чистятся (`deleteUnclaimedAttachments`). После F5 сессия выглядит «чистой» — ни ошибки, ни вопроса.
2. **Подсказка требует ручной работы.** Текст «удали Q&A-пару с файлом» — пользователь сам ищет сообщение, сам жмёт Delete под вопросом.
3. **Вопрос после F5 не восстановить** — транзитный возврат в поле ввода живёт только до перезагрузки.

## Решение №3 — персистентная плашка на сессию

**Хранение: `sessions.last_send_error` (TEXT, JSON | NULL).** Единственное место, переживающее F5: провальная отправка не пишет ничего в messages/attachments, а плашка привязана к сессии.

Схема: колонка в CREATE TABLE + guarded ALTER для legacy-БД (`ensureColumns`, паттерн attachment-cascade). Читается фронтом бесплатно — GET /api/sessions и /:id используют `SELECT *`.

**Снапшот (пишет chatController):**

```json
{
  "kind": "context_overflow" | "server",
  "providerName": "llama_cpp",
  "failedText": "текст вопроса",
  "fileNames": ["report.pdf"],
  "estimatedTokens": 3937667, "contextLength": 98304,   // пре-флайт (chars/4)
  "nPromptTokens": 3937667, "nCtxTokens": 98304,        // жёсткий 400 llama.cpp
  "message": "raw-текст ошибки провайдера",
  "at": "ISO"
}
```

**Точки записи (все в try/catch — не роняют обработчик ошибки):** пре-флайт-отказ chat-ветки (№1), catch chat-ветки (классификация `classifyProviderError` по `error.details` — тот же контракт, что проброс на фронт), catch vision-ветки (там `failedText` = `message || ''`), outer catch («Failed to process message»). `fileNames` — из `currentAttachments` (собирается в `sentFileNames` рядом с `sentFileIds`).

**Точки очистки:** успешная отправка (chat + vision, перед res.json), явный dismiss, смерть сессии (FK-каскад). **Не чистится** при удалении Q&A-пары — плашка честно продолжает показывать «последняя отправка не удалась», гасится следующим успехом/dismiss.

**Роут:** `DELETE /api/sessions/:id/send-error` (dismiss крестиком; 404 на чужую сессию).

**Фронт:** `sessionStore.persistedSendError` — `SendErrorInfo | null`, собирается `buildPersistedSendErrorInfo(raw, sessionId)` (sendError.ts, чистая функция) во **всех четырёх** точках открытия сессии (init savedActive-ветка, switchToViewing, returnToCurrent, loadViewingSession); при открытии сессии сначала сбрасывается в null (плашка не «переезжает» с предыдущей), мусор в столбце → null. Успешная отправка гасит локально (сервер чистит в той же точке). `dismissPersistedSendError` — локально сразу, DELETE best-effort.

**Рендер (`chat-area.tsx`):** плашка над композером, **если нет транзитного баннера этой сессии** (транзит — «живая» ошибка текущей страницы, у неё приоритет и полный набор действий). Стиль — приглушённый (border-destructive/30, bg-destructive/5), время провала бейджем (`formatSendErrorTime`, ru-RU, невалидное ISO → без бейджа). `failedFileNames` вшиты в detail («Вложения: report.pdf»), отдельных чипсов нет.

**Осознанные ограничения:**
- Network-провалы (бэкенд недоступен, status 0) не персистятся — писать некому; в этом случае есть только транзитный баннер.
- File-объекты не переживают F5 — персистентная плашка НЕ возвращает вложения в композер (только имена); вернуть можно вопрос (кнопка №4).
- Обновление `updated_at` при записи не делается: провал не поднимает сессию наверх списка.

## Решение №4 — быстрые действия в плашке

Кнопки одним кликом вместо ручного поиска (в обеих плашках):

1. **«Удалить пару с файлом»** — только для `kind === 'context_overflow'` и только если в сессии есть такая пара: `findLatestFileQAPairId(messages)` — последняя user-пара, чьи `attachments_meta` несут инжектящийся файл. `isInjectingFileMeta`: `kind` document/code → да; image/reference → нет (картинки не входят в `[Материалы]` — фильтр contextBuilder); optimistic-мета без kind → не-`image/*` mime считается файлом. Удаление — существующий `deleteMessage(questionId)` (каскад реестра, тост как у Delete под вопросом); после удаления кнопка исчезает (пересчёт по messages), «Повторить» отправляет вопрос заново уже без реинъекции старого файла.
2. **«Новая сессия»** — существующий `clearChat()` (архивирует текущую unsaved-сессию, создаёт новую, переключается) — выход из переполненной сессии без ручного перехода в сайдбар.
3. **«Вернуть вопрос в поле ввода»** (только персистентная) — `setInputValue(failedText)`: закрывает «не терять вопрос» и после F5. Заменяет текущее содержимое поля — действие явное, скрытых веток нет.

Транзитный баннер: «Повторить» + быстрые действия + крестик (как было). Персистентная плашка: «Вернуть вопрос» + быстрые действия + крестик.

## Что не вошло (осознанно)

- Авто-тримминг `[Материалы]` с повтором (№5) — политика инъекции файлов за владельцем.
- Черновик поля ввода в localStorage — отдельная тема (фиксирует ЛЮБОЙ незавершённый текст, не только провальный).
- Плашка в списке сессий (сайдбар) — только в чате открытой сессии.
- «Удалить пару с файлом» для PROJECT-reference — reference не каскадится и управляется правой панелью.

## Ручная проверка (владелец, DoD)

1. Кейс №22: большой PDF → баннер «Контекст переполнен» с числами → **F5** → сессия открыта, над композером приглушённая плашка «Контекст переполнен · ДД.ММ, ЧЧ:ММ», вопрос восстановим кнопкой «Вернуть вопрос в поле ввода».
2. На персистентной плашке (сценарий с ранее успешной парой с файлом): «Удалить пару с файлом» → пара исчезает из чата, кнопка пропадает → «Повторить» на транзитном баннере (или повторная отправка) проходит.
3. «Новая сессия» из плашки → новая сессия активна, старая заархивирована.
4. Крестик плашки → плашка исчезла и **после следующего F5 не возвращается** (dismiss персистентен).
5. Успешная отправка в сессии с плашкой → плашка исчезла (и локально, и в БД).
6. Остановить llama-server → отправка → транзитный баннер → F5 → плашка «Отправка не удалась» с текстом ECONNREFUSED.
7. Обычный диалог — плашки нет, поведение как раньше.
