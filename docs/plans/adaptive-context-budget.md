# ТЗ adaptive-context-budget: адаптивный char-бюджет истории (№3) + кап на message (№4)

**Статус:** исполнено в ветке `feat/adaptive-context-budget` → PR в `main`.
**Источник:** восстановленный владельцем нумерованный список (2026-11-11, процитирован в чате дословно) + вердикт «делаем №3+4». №3 — «Корень — адаптивный бюджет», №4 — «Кап на message».

## Нумерация: восстановленный список владельца (авторитетный)

1. UX-минимум (пре-флайт + баннер) и 2. «Не терять вопрос» — **смержены** (PR #22, `feat/context-overflow-ux`).
2. **№3 — адаптивный бюджет**: измеренная плотность charsPerToken вместо константы «4 символа = 1 токен»; `бюджет = ctx * измеренная_плотность * 0.9`.
3. **№4 — кап на message**: вставка длиннее ~64К символов → мгновенный 400 с понятным текстом; закрывает канал «3.9M из поля ввода».
4. №5 (авто-retry с пересборкой контекста) и авто-тримминг `[Материалы]` — **в этот трек не входят** (политика инъекции файлов — отдельное решение владельца).

**Важно (расхождение нумерации).** Ветка `feat/send-error-persist-actions` (ждёт merge владельца) исполнила ДРУГУЮ пару под теми же номерами: «№3 — персистентная плашка (переживает F5)» и «№4 — быстрые действия в плашке» — это реконструкция из старой внутренней нумерации ТЗ `context-overflow-ux.md`, исходный чат-список тогда в репо не попал. Работа самостоятельная ценная (F5 стирает инцидент, ручной поиск пары), но пункты 3/4 списка владельца — не она. Этот трек закрывает именно их.

## Корень (почему бюджет фиксированный — плохо)

`buildLLMContext` резал Q&A-историю по `maxChars = contextSize * 4` — эвристика «4 символа = 1 токен», откалиброванная под английский. На кириллице и коде реальная плотность 1.3–2.5 символа/токен (WORKLOG stats-size): бюджет в символах завышен в 1.6–3 раза → в контекст помещается «по эвристике» в 2 раза больше истории, чем по факту, и переполнение ловится только пре-флайтом (№1) или жёстким 400 llama.cpp вместо честного тримминга. Симптом-маркер — бар 12% vs фактические 38% (закрыто в #21 со стороны отображения, но серверный бюджет оставался эвристическим).

## Решение №3 — адаптивный бюджет по измеренной плотности

**Измерение (без новых запросов к LLM).** chatController (chat-ветка, успех) считает `promptChars` — символы промпта этого хода (`fixedChars + actualHistoryChars + questionChars + 64` обвязки, те же слагаемые, что у пре-флайта) — и складывает в `metrics` assistant-сообщения: `metrics = { ...result.metrics, promptChars }` (столбец messages.metrics — TEXT JSON, схема не меняется). Вторая половина измерения — `inputTokens`: у llama.cpp это теперь **полный** размер промпта.

**inputTokens = полный промпт (исправление источника).** README llama-server: `timings.prompt_n` — «number of prompt tokens being processed» (только вновь обработанные; кэш-хиты — `cache_n`). При включённом слот-кэше prompt_n ≈ размер ХВОСТА промпта — по нему плотность завышается на порядки. Цепочка источников `extractLlamaCppMetrics`:
1. `usage.prompt_tokens` — OpenAI-совместимый usage (llama.cpp ставит `slot.n_prompt_tokens`, полный промпт — то же поле, что в 400-ошибке);
2. фолбэк `timings.prompt_n + timings.cache_n`;
3. последний фолбэк `timings.prompt_n` (сборки без usage/cache_n).
Скоростные метрики (`promptTps` = prompt_n/prompt_ms) остаются на timings — они про обработанные токены. В metrics добавляется `cachedTokens` (диагностика). Ollama-путь (`extractMetrics`, `prompt_eval_count`) не менялся: у Ollama нет числа кэш-хитов, измерение на кэш-ходах уйдёт вне полосу и отфильтруется (см. ниже) — фолбэк-эвристика.

**Плотность и бюджет (`contextBuilder.resolveCharsPerToken` — экспорт, чистая функция).** С конца истории берём последнюю assistant-метрику, где `promptChars > 0`, `inputTokens >= 64` (защита от вырожденных ходов) и `плотность = promptChars / inputTokens` в полосе **[1.0; 5.0]** (вне полосы — кандидат пропускается, ищем дальше назад; мусор/не-JSON — пропуск). Ни одного достоверного кандидата → `{ charsPerToken: 4, source: 'default' }` — поведение до ТЗ.

```
maxChars = measured  ? floor(ctx * density * 0.9)   // 0.9 — запас на вариативность токенизатора
         : otherwise ? floor(ctx * 4)               // как раньше, без запаса
availableChars = max(maxChars - fixedChars, 0); targetChars = availableChars * retainPercent/100
```

На кириллице (плотность ~1.8) бюджет истории сам ужмётся в ~2.2 раза; на английском (~3.6–4) останется прежним ±10%. `info` получает `charsPerToken` и `charsPerTokenSource` (`'measured'|'default'`) — видны в логе «Context built» и в `contextInfo` ответа.

**Преф-флайт (№1) — на той же плотности.** `estimatedPromptTokens = ceil(promptChars / charsPerToken)` — числитель общий (`promptChars`). С измеренной кириллической плотностью оценка совпадает с реальностью в разы точнее chars/4: file-driven переполнение ловится раньше и честнее. Моки в тестах без `info.charsPerToken` → фолбэк 4 (старые тесты пре-флайта не тронуты).

**Бонус — бар диалога.** `inputTokens` стал полным промптом → накопительная токеновая статистика сессии (#21) перестаёт недосчитывать кэш-хиты, бар синхронизируется с реальностью и с бюджетом сервера («заодно и бар с эвристикой сервера синхронизируются»).

**Vision-ветка:** `promptChars` НЕ пишется (base64-картинку токенизирует mmproj, char-плотность неприменима) и `resolveCharsPerToken` такие ходы пропускает, находя последний текстовый. У Ollama-ходов плотность может быть недостоверной на кэш-ходах — полоса отфильтрует, сработает фолбэк.

## Решение №4 — кап на message (~64К символов)

**Сервер (`chatController.MAX_MESSAGE_CHARS = 64000`, экспорт):** первая проверка в try, ДО URL-обработки и реестра вложений — мгновенный 400 без побочных эффектов:
`400 {error, code:'message_too_long', messageLength, maxMessageChars}`. Семейство прочих 400-валидаций: persist-плашки нет (строк реестра ещё не существует, вопрос не теряется — фронт всегда откатывает failedText). Граница: ровно 64000 проходит.

**Фронт (`frontend/src/lib/messageCap.ts` — новый, чистый + тесты):** `MAX_MESSAGE_CHARS = 64000` (дубликат серверной константы — синхронизировать оба места, паттерн DEFAULT_SYSPROMPT), `isMessageOverCap`, `isMessageNearCap` (>90% капа — «мягкая» пометка), `formatChars` (64000 → «64 000»). Композер (`chat-area.tsx`): при over-cap — Send заблокирован (и кнопка, и Enter через guard в `handleSend`), в футере под композером разрушающая подсказка «Слишком длинный ввод: N / 64 000 символов — сократи вопрос или вынеси часть в файл»; при near-cap — нейтральный счётчик N / 64 000. Вставка > капа не отправляется вообще — серверный 400 остаётся для прямых запросов.

**Баннер (`sendError.ts`):** `ApiError` с `code:'message_too_long'` → kind `server` (это не переполнение контекста модели), title «Слишком длинный ввод», detail с числами (`formatChars`). Механика PR #22 (откат вопроса в поле ввода) работает без изменений.

## Ручная проверка (владелец, DoD)

1. Кириллическая сессия (пара Q&A на русском, ctx модели 98304): после первого ответа следующий ход в логе «Context built» показывает `charsPerToken ≈ 1.3–2.5, source=measured`, история обрезается заметно раньше, чем раньше.
2. Новый чат (без метрик): первый ход — `charsPerToken 4, source=default`, поведение как до ТЗ.
3. Вставить в поле ввода >64К символов → Send серый, подсказка «Слишком длинный ввод…», Enter не отправляет; урезать до <90% — счётчик исчезает.
4. Вставить ровно 64 000 символов → отправка уходит (граница снизу).
5. Прямой запрос к API с message >64К → мгновенный 400 `message_too_long` (проверка контракта).
6. Бар контекста после нескольких ходов показывает полный промпт (с кэш-хитами не занижается).
7. Vision-ход не сбивает плотность: после vision-вопроса следующий текстовый ход использует последнюю текстовую метрику.
